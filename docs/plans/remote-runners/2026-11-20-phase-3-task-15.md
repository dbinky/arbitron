## Accepted request and local policy

P3 T8's serialized `AgentDispatch`, WireAgent and runneragent.AgentJob carry request facts only: exact Model, canonical Provider, Backend, ContextWindow, Effort, effective ToolScope, RequireExecutedModel, workdir, prompt/session and timeout. Remove `Capability *provider.BackendCapability` from all three mirrors, translators, tests and payloads; server rules are not a runner-local capability producer. `adapter/runnerproto` retains its stdlib/uuid-only dependency boundary. P2 T9 `BuildCapabilities` and the actual runner executor consume the SAME loaded local Rules; reject unsupported axes before accept rather than disabling policy through zero-value rules or silently flooring a different request.

For remote subscription execution, reconstruct the binding with the source's verified local Provider, exact model/backend/context/effort, `AllowedTools` from the effective accepted scope and `Pinned: RequireExecutedModel`; no server credential/URL/RevealKey is installed. Validate requested route/family/backend against local source evidence. `RequiresModelEvidence`/native result checks must enforce strict model equality when required; a wrong/missing native model record fails before push/commit even if a response labels itself with the requested model. Preserve native executed-model evidence in the result/trace. A matching request label alone is not proof.

At the server routing boundary, `RunAgent` constructs requirements with the actual AgentMission.ToolScope (profile scope, node fallback or already resolved deployment scope), not only binding.AllowedTools. P1 T10 owns this mapping; this task extends its tests and P3 root tests. An empty scope's existing global-default semantics must be resolved before remote dispatch so another runner cannot widen it. The current inner factory is the production source for the configured effective tool scope; use P3 T8's request-policy helper in routing. Consume P3 T8's implemented `adapter/provider/agent_policy.go:Factory.EffectiveAgentTools(binding provider.ResolvedBinding, requested []string) ([]string,error)` from the same config/per-binding precedence used by AgentProviderFor; P3 T13 passes that helper into routing via `runner.AgentToolPolicy` (domain function port), and P4 T3 freezes its result for interactive agents. Never infer “all tools” from an empty advertised list.

## Wiring

`cmd/arbitron-runner/build.go:buildAgent` loads config/rules once, resolves the native binaries, constructs WorkspaceJobs with its actual Syncer/BundleCache/Process/HarnessRunner/Rules, then passes those same configs/rules and enabled flags to Discover. Source inventory flows through Agent hello/heartbeat → wsclient → HTTP translator → registry → Place/atomic Reserve → remote runner. P3 T13 supplies the server tool-policy helper. P4 T13 reuses this graph for session advertisement and does not invent a separate Codex source. Rule parsing failure or missing required wiring fails startup/advertisement visibly; no nil Rules fallback.
