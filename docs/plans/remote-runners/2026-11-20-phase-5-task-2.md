# Remote Runners — Phase 5 Task 2: Authoritative live snapshots and polling

**Spec / Design references:** `docs/specs/2026-11-19-remote-runners-spec.md`; `docs/designs/2026-11-19-remote-runners-design-phase-5.md` (sections mapped below).

**Goal:** Pool and runner detail update promptly from authorized REST data when system events arrive; disconnected sockets show stale status and poll. No delayed event or HTTP response rolls newer state backward.

**Correction:** Existing list/detail/events/instances endpoints are independent reads with no shared revision/cursor. The previous id/At watermark reducer, event-derived health/liveness/slot patches, `seenEvents` as proof a runner snapshot includes a log entry, and timestamp-only execution patching are removed. Events invalidate snapshots. Event-log IDs deduplicate only the displayed log. This requires no new server endpoint/cursor and leaves server authorization authoritative.

`upsertExecution`/`pruneExecutions` remain pure utilities for already-authoritative snapshots; consumers MUST NOT apply unversioned system events with them. `applyLiveEvent` returns the same data state plus `refetch:true` for relevant pool/source/job/execution/workspace/session/node-completion events, and unchanged/refetch false for unknown events. A pool event may be appended/deduplicated as log display only; it never asserts that health/count/telemetry/execution is reflected in REST. `useRunner` scopes invalidations to its runner or visible run assignments; ambiguous source-only events can invalidate conservatively.

## Hook algorithm

1. Serialize loads per subject epoch: one active REST load at a time, plus one dirty flag for coalesced invalidations. An event during a load marks dirty and schedules one fresh load AFTER the active load finishes. Never replay buffered events as data patches atop the result. If data arrived before an event, the next load captures its authoritative state; if event races a read, dirty followup closes the race.
2. Increment epoch on subject/auth/enabled change or unmount. Ignore old epoch successes AND errors and cancel scheduled work. A load started for runner A must never populate runner B. No stale request can overwrite a more recently requested subject or clear that subject's error/loading state.
3. Initial load and manual retry call load; error preserves last successfully read data with `error` and `stale=true`. A REST failure also marks data stale while WebSocket remains connected. Coalesce events/manual retries/poll/reconnect; ensure failed loads don't starve dirty followup, bounded by debounce/backoff.
4. Disconnect sets stale immediately and starts 5s polling; reconnect triggers an authoritative refresh. Connected 15s refresh updates telemetry because heartbeats need not be bus events. A failed freshness refresh keeps stale until a successful load. Socket connected alone does not prove data freshness.
5. `loadPool` may issue independent runners/events/running/waiting GETs concurrently, then deduplicates execution rows by durable job identity. It MUST NOT label this a transactional snapshot or derive revision from event timestamps. Read states holding pending/recovery work as the upstream projector supports, including waiting interactive runs. Runner detail returns `{detail,pool}`: detail is the authoritative detail response, pool is snapshotState([detail], filteredEvents, authorized assignment execution data); applyRunnerEvent invalidates this subject without patching detail/pool from events. None of these read hooks loads/stores runner-key plaintext.
6. Countdown uses absolute reset timestamp, validates finite dates, clamps display at zero/awaiting confirmation, and never mutates source health after reset. `useNow` drives rendering; unavailable timestamps remain unknown.

## Wiring and sink assertions

`usePool` → PoolView (T3) → `/pool` App route (T8). `useRunner` → RunnerDetailView (T5) → `/pool/runners/:id` (T8). `useSystemWebSocket` supplies invalidations from actual system stream. REST functions reach P1–P4 authorized service projections. Tests mount real hooks/views and real decoder/fetch layer; only transport is faked. Initial data and a changed authoritative reply must contain nonempty real-shaped source/assignment/session/resource fields. Removing list/get hook injection or dropping event subscription must fail the final rendered runner/card/assignment assertion.
