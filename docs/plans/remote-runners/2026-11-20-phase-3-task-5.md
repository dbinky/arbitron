# Remote Runners — Phase 3 Task 5: Validated durable completion and replay (RR-10)

**Goal:** A completed node has one durable result/variables/continuation fact linked to every exact dispatched operation and workspace candidate. Restart repeats uncommitted operations from the prior committed checkpoint and replays committed operations without repeating them.

**Spec/design:** `docs/specs/2026-11-19-remote-runners-spec.md`, Recovery and session continuity; `docs/designs/2026-11-19-remote-runners-design-phase-3.md` §3.3, §3.5, §6, §8. Shared contracts: `2026-11-20-contracts.md` §3, §4, §8, §11, §16. This replaces the previous task text in full: last-placement inference, latest-checkpoint fallback, and dispatcher completion before executor validation are removed.

**Dependencies:** P1 T2 invocation/identity; P1 T8/T10 dispatcher/routing; P1 T14 trace; P3 T1 schema; P3 T2 immutable prepared candidates; P3 T3 resource leases. Defines the receipt contract before P3 T6 implements producers. Domain never imports adapters.

## Interfaces — produced here

```go

type JobFenceRef struct { JobID uuid.UUID; RunnerID string; Generation int64 }

}

```

`Record` rejects zero job ID/runner/generation, zero resource token/key/owner/generation, empty workspace ref, mismatched duplicate job receipts and a ref belonging to another run. Identical receipts are idempotent. Multiple suboperations under one invocation remain distinct; a last placement trace entry cannot replace them. Returned slices/objects are defensive copies.

Adapter: `adapter/sqlite/step_commit_repo.go:StepCommitRepo`; `NewStepCommitRepo(db *sql.DB) *StepCommitRepo`. It implements `engine.StepCommitter` with the SAME DB used by runner jobs, prepared checkpoint catalog, resource leases, instances, node executions and invocations.

## Interfaces — consumed, not redefined

- `engine.InvocationStore.Begin(ctx,runID,nodeID) (Invocation,error)`, `.Commit(ctx,invocationID) error`, `.Get(ctx,invocationID) (Invocation,error)` from P1 T2. One invocation per node visit; a loop revisit is a new invocation, restart reuses the open one.
- `runner.Fence{JobID,RunnerID,Generation}` and the single ledger fence from P1 T6; `checkJobFenceTx` and resource-fence transaction helpers must validate active exact generations. A `completed` state is accepted only for an already committed idempotent replay, never to authorize a new commit.
- P3 T2 `CheckpointCandidate{Ref,Base,Job,Resource,ArchivePath,SizeBytes}`. Prepared bytes are fsynced before this task's DB transaction. `workspace_homes.checkpoint_version` selects committed progress; inserting a prepared candidate cannot change it.
- P3 T3 durable `workspace_leases`, active holder token/generation and owner. A home row records location and is not exclusive execution ownership.
- P3 T1 044 `step_commits`, `step_commit_operations`, checkpoint state/fence columns. All operation receipts are persisted in `step_commit_operations`; do not add singular last-job/checkpoint projections.

## Wiring and producers

| Field/collaborator | Production producer | Composition root/consumer |
|---|---|---|
| `StepCompletionSink` | `Engine.executeWithRetry` creates a fresh sink per workflow retry attempt before calling an executor; P1 `StepIdentity` still identifies invocation/suboperation | run loop retains that sink through output validation and `commitNodeSuccess` |
| Job receipts | `StepDispatcher` after exact assignment/result; P3 T6 writes `StepOutput.Completion`, routing records it in the sink | routed selectors/process runner share invocation context; missing production sink fails closed |
| Workspace receipt | P3 T6 `WorkspaceSync.StageBuiltIn`/`AcceptPush` exact prepared ref + lease, never `Latest` | `StepCommit.Completions` |
| Execution/result/variables/next node | `executeWithRetry`, executor validation and `findNextNode` | `commitNodeSuccess` passes these and exact sink receipts |
| `StepCommitRepo` | `NewStepCommitRepo(db)` | P3 T13 `eng.SetStepCommitter(mobility.Commits)` and same object in recovery |
| Replay | persisted `step_commits` + `step_commit_operations` | engine checks open invocation before executing; recovery uses same committer |

An inner transport returning success does not complete the ledger job. In production routed mode dispatcher must keep its job/resource active until this transaction. An explicitly configured legacy non-routed test executor may have no receipts; it still propagates persistence failures. Omitting the committer/sink in the production root is a startup error.

### Cycle 3 — SQLite all-or-nothing commit

Write `TestStepCommitRepo_CommitIsOneTransactionAndReplayable`, `TestStepCommitRepo_MissingWorkspaceCandidateFailsClosed`, `TestStepCommitRepo_BuiltInCandidateIsLinked`, `TestStepCommitRepo_StaleResourceRollsBackAll`, `TestStepCommitRepo_AllSuboperationsCommitAtomically`, `TestStepCommitRepo_ExecutionRunMismatchRejected`, and `TestStepCommitRepo_FailureAfterPromotionRollsBackEverything`. Run `go test ./adapter/sqlite/ -run TestStepCommitRepo -v`; expect undefined repository first.

Implement one transaction:

1. Verify invocation/run/node and `Execution.InstanceID == RunID`, `Execution.NodeID == NodeID`, execution identity and receipt completeness. Reject conflicting replay; an exactly matching existing commit returns the durable result idempotently.
2. Validate every exact active job fence and resource token/owner/generation/holder. Verify each workspace candidate is prepared for that same run/job/resource and its base equals the current committed pointer. Require its retained immutable artifact record; empty/missing candidates are errors, including built-in jobs. No newest-row query or implicit fallback is permitted.
3. Insert the node execution and complete all included jobs; update their attempt outcomes/results. Mark exact candidate(s) committed, advance home pointer(s), clear dirty and release exact resource claim(s).
4. Persist all operation receipts, result/variables, next continuation, invocation state and `step_commits`; then commit. Any error rolls back every row/pointer. Candidate artifacts remain unreferenced, never current progress.

Nonterminal commits atomically mark the invocation committed and set the next node. Terminal commits retain the current open invocation and terminal replay record until `SetCompleted` succeeds, so restart can replay without dispatch. After successful terminal state persistence mark the invocation committed. The already durable terminal result must never execute again due to an invocation-close failure.

## Successful suspension commit (required)

Add `StepCommit.Mode StepCommitMode` (`StepCommitAdvance`, `StepCommitSuspend`) and `Suspension *StepSuspension` where `StepSuspension{Kind string; ChildLinkID *uuid.UUID; State map[string]any}` names the durable wait/child-link state. `StepCommitSuspend` atomically persists validated suboperation results/receipts and the existing child link/wait state, completes/releases their runner jobs/resources, and keeps the invocation OPEN/current node unchanged. It does not invent a successful node execution or advance an edge. Persist suspension records keyed `(invocation_id,operation_id)` in 044; restart resumes the SAME child link/prepared results without repeating the preparer LLM. The spawn service produces its durable child-link ID and validated prepared input state; the engine performs suspension commit after an awaited spawn returns `Wait` and before exposing the wait. A missing child-link/receipt causes visible parent failure/recovery; any already durable/started child link is retained and reused, never rolled back by assumption and never duplicated. On child completion the final node commit extends the invocation using its already committed suboperation receipts without double-completing them. P4 first turns use their own atomic TurnCommit; receipts already consumed there must not be committed again by this boundary.

Write `TestEngine_SuspendCommitReleasesSuboperationSlotKeepsInvocationOpen`, `TestEngine_SuspendRestartReusesChildAndPreparedInputs`, and `TestEngine_SuspendCommitFailureCreatesNoDuplicateChild` RED before implementation. P3 T13 root test sets step limit 1, uses an awaited spawn needing child-input LLM preparation, and proves its child executes while the parent visibly waits; zero job slots are held by the waiting parent.
