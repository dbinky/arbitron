# Paired Reviews — Latest Model Profiles

Phase 2 runs only after every single-system box in `docs/reference/focus-areas.md`
is ticked. A row joins two behaviours only when all three of these hold:

- they share persisted state, a wire contract, a flag or an ordering;
- different tasks, phases or commits built the two sides;
- each side passes in isolation while the combination is wrong.

One approval covers both directions. Trace the TRACE path, then show that BREAK is
impossible, either with a test that goes red or with a guard cited at `file:symbol`.
Area numbers refer to `focus-areas.md`, and `G` numbers to `gaps-identified.md`.

**Budget:** 10 singles × 2 + 15 paired = 35 minimum passes ≤ 500 × 0.35 = 175.

## No seam

All 45 combinations of the 10 areas were considered: 15 are paired above and 30 are
recorded below. No seam is deferred for budget.

### Inside one behaviour

- Area 1 ↔ Area 3: the Claude isolation commit `d0d3522b` changed the adapters real runs use (`chat_adapter.go`, `agent_adapter.go`, `stream_agent_adapter.go`), and in the same commit it switched to the probe recipe only on `SuppressTools`. Pin propagation into Claude and Codex is Area 3 wiring check 6. "Ordinary runs unchanged" is Area 3 folded check 4, and the probe-limit context leak is Area 3 failure check 7.
- Area 2 ↔ Area 3: batch binding → pi, OpenCode or HTTP verifier is the same execution path, and the pi flags were added with their ordinary-run control in the same commit `2a92077b`. This is Area 3 wiring check 6 and Area 2 wiring check 2.
- Area 1 ↔ Area 6: `HandleMessage`/`Execute` → `RequireExecutedModel` → the Claude or Codex stream verifier is internal continuation wiring, and the `SuppressTools` branch in the stream adapters came from the same probe commits. This is Area 6 wiring check 5 and folded check 3.
- Area 2 ↔ Area 6: HTTP stream identity validation before the turn is persisted is the continuation sink itself (Area 6 wiring check 6, failure check 3).
- Area 1 ↔ Area 2: the lanes share only the router dispatch, `claudecli.RunSpec`/`execRunner` and `procenv` probe limits, built in one P3T4 slice (`28b8afe3`). Each lane owns its own verifier and restriction recipe, so no independently built state is handed off. Runner teardown is G16, shared by both areas' failure lenses.
- Area 3 ↔ Area 5: both are sub-paths of the same trigger capture (`captureModelPins`, `ModelPinSnapshot`), built by the same P1T3 task and split only by route kind. The hand-off from `Models` to `OpaqueRoutes` is Area 5 wiring check 1.
- Area 3 ↔ Area 6: the shared `PinLookup`/`PinningResolver` contract was built by the same P1T3/P1T4 tasks, and the batch and continuation entries are separate areas. Ordering between pin release and a turn is Area 6 failure check 5.
- Area 3 ↔ Area 9: a seeded pinned profile reaches the trigger through the same `ValidateSelection`/`ValidatePinRoutes` write contract (Area 9 wiring check 1).
- Area 5 ↔ Area 6: `RequiresModelEvidence` at `conversation.go:248` and `executor_interactive.go:136` was added with the D8 enforcement in P1T4. The interactive D8 case is Area 5 wiring check 3 and Area 6 failure check 4.
- Area 5 ↔ Area 9: a seeded D8 pin uses the same `ValidatePinRoutes` contract as Area 7 (Area 9 wiring check 1).
- Area 7 ↔ Area 8: they share `PolicyRevision`, but `CandidateService.read` remaps retained raw models under the current policy, and a concurrent revision mismatch returns `ErrExecutionRevisionStale` explicitly (Area 7 failure check 5).
- Area 7 ↔ Area 9: admin create and YAML seed run the same `ProfileService` prepare/revalidate/store flow (`PreparedSelection`, `SeedBatch`) from the same P2T2 task. They differ only by entry.
- Area 8 ↔ Area 9: the seed consumes classification only through `CandidateService`, which fails loudly on a stale policy, as in Area 7 ↔ Area 8.
